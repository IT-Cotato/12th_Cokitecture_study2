# 4장. 분산 메시지 큐

### 메시지 큐

> 인터페이스를 경계로 나뉜 블록 사이의 통신과 조율을 담당
> 
- 결합도 완화: 각 블록을 독립적으로 갱신 가능
- 규모 확장성 개선: 데이터 생상자 - 소비자 시스템 규모를 트래픽 규모에 맞게 조절 가능
- 가용성 개선: 특정 컴포넌트 문제시 다른 컴포넌트 사용 가능
- 성능 개선: 비동기 통신 가능

# 1단계: 문제 이해 및 설계 범위 확정

### 기능 요구사항

- 생산자는 메시지 큐에 매시지 전송 가능
- 소비자는 메시지 큐를 통해 메시지 수신 가능
- 메시지는 반복/한 번 수신 가능
- 오래된 이력 데이터는 삭제 가능
- 메시지 크기는 킬로바이트 수준
- 메시지 생산 순서대로 소비자에게 전달 가능
- 메시지 전달 방식은 설정 가능

### 비기능 요구사항

- 높은 대역폭/낮은 전송 지연 중 하나를 설정으로 선택 가능
- 규모 확장성: 메시지 양 급증해도 처리 가능
- 지속성 및 내구성: 데이터를 디스크에 보관. 여러 노드에  복제

### 전통적 메시지 큐와의  차이점

- 전통적 메시지 큐
    - 소비자에게 메시지가 전달되는 시간만큼 메모리에 보관
    - 전달 순서 보존 X

# 2단계: 개략적 설계안 제시 및 동의 구하기

### 메시지 큐 핵심 컴포넌트 및 상호작용 흐름

- 생산자는 메시지를 메시지 큐에 발행
- 소비자는 큐를 구독하고 구독한 메시지를 소비
- 메시지 큐는 생산자와 소비자 사이의 결합을 느슨하게 하는 서비스
    - 생산자와 소비자의 독립저깅ㄴ 운영 및 규모 확장을 가능하게 함
- 생산자와 소비자 모두 클라이언트/서버 모델 관점에서 보면 클라이언트고 서버는 메시지 큐. 네트워크 통신

## 메시지 모델

---

### 일대일 모델

> 큐에 전손된 메시지는 한 소비자만 가져감
> 
- 소비자가 메시지 가져가면 해당 메시지는 큐에서 삭제
- 데이터 보관 지원 안함

### 발행-구독 모델

> 토픽을 이용하여 메시지 교환
> 
- 토픽: 메시지를 주제별로 정리
- 토픽에 전달된 메시지는 해당 토픽을 구독하는 모든 소비자에게 전달

## 토픽, 파티션, 브로커

---

### 파티션

> 토픽에 보낼 메시지의 작은 부분집합
> 
- 샤딩과 동일
- 토픽을 여러 파티션으로 분할하여 메시지를 모든 파티션에 균등하게 분할
- 메시지 큐 클러스터 내의 서버에 고르게 분산 배치
- 브로커: 파티션을 유지하는 서버
- 토픽 용량 확장시 파티션 개수 늘림
- FIFO 큐처럼 동작: 같은 파티션 내에서 메시지 순서 유지
- offset: 파티션 내의 메시지 위치

### 소비자 그룹

---

> 토픽에서 메시지를 소비하기 위해 협력
> 
- 한 그룹 내의 소비자는 메시지를 병렬로 소비
    - 메시지 순서 보장 불가
- 파티션 하나당 한 소비자만 소비 가능
    - 일대일 모델에 수렴

## 개략적 설계안

---

### 클라이언트

- 생산자: 메시지를 특정 토픽으로 전송
- 소비자 그룹: 토픽을 구독하고 메시지 소비

### 핵심 서비스 및 저장소

- 브로커: 파티션 유지. 하나의 파티션은 특정 토픽에 대한 메시지의 부분 집합 유지
- 저장소
    - 데이터 저장소: 파티션 내 데이터 저장소에 보관
    - 상태 저장소: 소비자 상태는 이 저장소에 유지
    - 메타데이터 저장소: 토픽 설정, 토픽 속성 등을 이 저장소에 유지
- 조정 서비스
    - 서비스 탐색: 어떤 브로커가 살아있는지 알려줌
    - 리더 선출: 한 브로커가 컨트롤러 역할 담당. 클러스터 당 한 개의 활성 상태 컨트롤러 필요. 컨트롤러가 파티션 배치 책임

# 3단계: 상세설계

- 회전 디스크 사용
- 메시지 수정 없이 전송 가능
- 일괄 처리 우선

## 데이터 저장소

---

### 메시지 큐의 트래픽 패턴

- 읽기/쓰기 빈번
- 갱신/삭제 연산 발생 없음
- 순차적인 읽기/쓰기가 대부분

### 데이터베이스

- 관계형 데이터베이스: 토픽별로 테이블 생성. 토픽에 보내는 메시지는 해당 테이블의 새로운 레코드로 추가
- NoSQL 데이터베이스: 토픽별로 컬렉션 생성. 토픽에 보내느 메시지는 하나의 문서가 됨

### 쓰기 우선 로그

> 새로운 항목이 추가되기만 하는 일반 팡리
> 
- 지속성 보장하는 메시지에 유용
- 회전식 디스크 기반 저장장치는 큰 용량을 저렴하게 제공
- 파일을 세크먼트 단위로 나눔

## 메시지 자료 구조

---

> 메시지 자료 구조는 생산자, 메시지 큐, 소비자 사이의 계약
> 

### 메시지 키

- 파티션 결정시 사용
- 비즈니스 관련 정보 담음
- 키를 파티션에 대응시키는 알고리즘 이용시 파티션 수 달라져도 메시지 균등 분산 가능

### 메시지 값

- 일반 텍스트 및 압축된 이진 블록

### 메시지 기타 필드

- 토픽: 메시지가 속한 토픽 이름
- 파티션: 메시지가 속한 파티션 아이디
- 오프셋: 파티션 내 메시지의 위치. 메시지는 토픽, 파티션, 오프셋 세가지 정보를 알면 찾을 수 있음
- 타임스탬프: 메시지가 저장된 시각
- 크기: 메시지의 크기
- CRC: 순환 중복 검사. 데이터 무결성 보장

## 일괄 처리

---

> 생상자, 소비자, 메시지 큐는 메시지를 가급적 일괄 처리
> 

### 생산자 측 작업 흐름

- 라우팅 계층을 도입하여 브로커에 전송
1. 생산자는 메시지를 라우팅 계층으로 전송
2. 라우팅 계층은 메타데이터 저장소에서 사본 분산 계획을 읽어 자기 캐시에 보관
3. 메시지 도착하면 파티션-1의 리더 사본에 전송
4. 리더 사본이 메시지를 받고 해당 리더 사본을 따르는 다른 사본은 해당 리더로부터 데이터 수신
5. 충분한 수의 사본이 동기화되면 리더는 데이터를 디스크에 기록
6. 데이터 소비 가능

- 단점
    - 라우팅 계층 도입시 거칠 네트워크 노드가 증가하여 전송 지연 증가
    - 일괄 처리 여부 고려 안함

### 수정된 설계안

- 라우팅 계층을 생산자 내부로 편입
- 버퍼 도입
- 생산자 클라이언트 라이브러리의 일부로 생산자에 설치
- 장점
    - 전송 지연 감소
    - 메시지를 전송할 파티션 결정 로직 가짐
    - 전송할 메시지를 버퍼 메모리에 보관했다가 목적지로 일괄 전송하여 대역폭 증가 가능

## 소비자 측 작업 흐름

---

특정 파티션의 오프셋을 주고 해당 위치에서부터 이벤트를 묶어 가져옴

### 푸시 vs 풀

- 푸시모델
    - 낮은 지연: 브로커는 메시지를 받는 즉시 소비자에 전송
    - 소비자의 메시지 처리 속도 느리면 부하 발생 가능
    - 생산자가 데이터 전송 속도 좌우하므로 그에 맞는 컴퓨팅 자원 필요
- 풀 모델
    - 메시지 소비 속도를 소비자가 결정
    - 메시지 소비 속도가 느리면 소비자 추가/대기 가능
    - 일괄 처리에 적합
    - 컴퓨팅 자원 낭비. 브로커에 메시지 없어도 소비자는 데이터 풀을 시도
    - 롱 폴링 모드 지원

## 소비자 재조정

---

> 어떤 소비자가 어떤 파티션을 책임질 지 결정
> 

### 코디네이터

- 소비자 재조정을 위해 소비자와 통신하는 브로커 노드
- 소비자로부터 오는 박동 메시지를 살핌
- 각 소비자의 파티션 내 오프셋 정보를 관리
- 처리 흐름
    1. 시작: 그룹 내에 소비자 A만 존재. 모든 파티션 메시지 소비. 지속적인 박동 메시지 전송
    2. 소비자 B가 그룹 합류 요청
    3. 코디네이터가 모든 소비자에 수동 통지
    4. 모든 소비자 합류시 코디네이터가 리더 선출 후 알림
    5. 파티션 배치 계획 생성 후 코디네이터에게 전송
    6. 소비자는 자신에게 배치된 파티션의 메시지를 가져옴
- 소비자 삭제 흐름
    1. 소비자 A, B는 같은 소비자 그룹
    2. 소비자 A가 가동 중단 필요시 탈퇴 요청
    3. 코디네이터는 중지 통지
    4. 나머지 동일
- 비정산 가동 중단
    - 일정 시간 동안 박동 메시지 수신 없으면 사라진 것으로 판단

## 상태 저장소

---

### 사용 정보

- 소비자에 대한 파티션 배치 관계
- 각 소비자 그룹이 각 파티션에서 마지막으로 가져간 메시지 오프셋

### 상태 정보 이용 패턴

- 읽기/쓰기 빈번. 발생 양 적음
- 데이터 갱신은 빈번. 삭제되는 일은 없음
- 읽기 쓰기 연산은 무작위적 패턴 보임
- 데이터 일관성이 중요

## 메타데이터 저장소

---

- 토픽 설정, 속성 정보 보관
    - 파티션 수, 메시지 보관 기간, 사본 배치 정보 등

### 주키퍼

> 계층적 키-값 저장소 기능을 제공하는 서비스
> 
- 메타데이터와 상태 저장소를 주키퍼를 이용해 구현
- 브로커는 메시지 데이터 저장소만 유지
- 주키퍼가 브로커 클러스터의 리더 선출 과정 도움

### 복제

- 토픽-A파티션-1: 사본 3개. 리더는 브로커-1. 단순 사본은 브로커-2와 3에 배치
- 토픽-A파티션-2: 사본 3개. 리더는 브로커-2. 단순 사본은 브로커-3와 4에 배치
- 토픽-A파티션-3: 사본 3개. 리더는 브로커-3. 단순 사본은 브로커-4와 1에 배치

### 사본 동기화

- 메시지 소실 방지
- 생산자에게 응듭 받기 전 모든 사본 동기화

### ACK

- ACK = all
    - 생산자는 모든 ISR이 메시지 수신 후 ACK 응답 수진
- ACK = 1
    - 리더가 메시지 저장 후 바로 ACK 응답 수신
    - 응답 지연 감소
    - 리더에 장애 발생 시 메시지 영구 소실 가능
- ACK = 0
    - 수신 확인 메시지 대기 안 함
    - 계속 메시지 전송
    - 낮은 응답 지연을 위해 메시지 손실 감수

### ISR 요건을 만족하는 사본에서 메시지를 가져가지 않는 이유

- 설계 및 운영이 단순
- 특정 파티션의 메시지는 같은 소비자 그룹 안에서는 오직 한 소비자만 읽어감
- 인기 있는 토픽이 아니면 리더 사본에 대한 연결의 수는 많지 않음
- 인기 있는 토픽은 파티션 및 소비자 수를 늘려 규모 확장 가능

## 규모 확장성

---

### 생산자

- 그룹 단위의 조정에 가담 안 함
- 새로운 생산자 추가/삭제가 쉬움

### 소비자

- 소비자 그룹은 서로 독립적
- 새 소비자 그룹은 쉽게 추가/삭제 가능
- 같은 그룹 내 소비자가 새로 추가/삭제/장애로 제거시 재조정 메커니즘이 맡아 처리

### 브로커

- 브로커 사본에 메시지가 많을수록 안전
    - 응답 지연 고려 필요
- 사본은 서로 다른 노드에 둘 것
- 사본 수와 위치 결정시 데이터 안전성, 자원 유지에 드는 비용, 응답 지연 등을 고려
- 브로커 노드 추가/삭제시 사본 재배치
- 한시적으로 시스템에 설정된 사본 수보다 많은 사본 허용

### 파티션

- 지속적으로 보관된 메시지: 기존 파티션에 존재, 해당 데이터 이동 X
- 새로운 파티션 추가: 그 이후 메시지는 3개 파티션 전부에 지속적으로 보관
- 파티션 삭제
    - 파티션 삭제 결정시 새로운 메시지는 다른 파티션에만 보관
    - 퇴역된 파티션은 일정 시간 동안 유지
    - 파티션 퇴역 후 실제로 제거가 이루어지는 시점까지 생산자는 메시지를 남은 두 파티션으로만 전송
    - 실제 파티션 제거 시점 오면 생산자 그룹은 재조정 작업 개시

## 메시지 전달 방식

---

### 최대 한 번

- 메시지 소실 시 재전송 안 함
- 생산자는 토픽에 비동기적으로 메시지 전송. 수신 응답 대기X
- 소비자는 메시지 읽고 처리 전 오프셋 갱신
- 소량  데이터 손실을 감수하는 애플리케이션에 적합

### 최소 한 번

- 생산자는 메시지를 동기적/비동기적으로 보낼 수 있음
- 메시지가 브로커에게 전달되었음을 반드시 확인
- 메시지 전달 실패/타임아웃 발생 시 계속 재시도
- 소비자는 메시지 처리 후에만 오프셋 갱신

### 정확히 한 번

- 지불, 매매, 회계 등 금융 관련 응용에 적합
