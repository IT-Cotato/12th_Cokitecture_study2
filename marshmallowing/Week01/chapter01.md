### 기능 요구사항

- 사용자의 위치(경도와 위도 쌍)와 검색 반경 정보에 매치되는 사업장 목록을 반환
- 사업장 소유주가 사업장 정보를 추가/삭제/갱신할 수 있도록 하되, 그 정보가 검색 결과에 실시간으로 반영될 필요는 없다고 가정
- 고객은 사업장의 상세 정보를 살필 수 있어야 함

### 비기능 요구사항

- 낮은 응답 지연(latency): 사용자는 주변 사업장을 신속히 검색할 수 있어야 함
- 데이터 보호: 위치 기반 서비스(LBS)를 설계할 때는 언제나 사용자의 정보를 보호할 방법을 고려해야 함
    - GDPR, CCPA 같은 데이터 사생활 보호 법안 준수
- 고가용성 및 규모 확장성: 인구 밀집 지역에서는 이용자가 집중되는 시간에 트래픽이 급증해도 감당할 수 있도록 설계

## 데이터 스키마

- business 테이블
    - 사업장 상세정보
- 지리적 위치 색인 테이블
    - 위치 정보 관련 연산의 효율성을 높이기 위해

## 로드밸런서

- 유입 트래픽을 자동으로 여러 서비스에 분산시키는 컴포넌트
- 로드밸런서에 단일 DNS 진입점(entry point)를 지정하고, URL 경로를 분석하여 어느 서비스에 트래픽을 전달할지 결정

## 위치 기반 서비스(LBS)

- 주어진 위치와 반경 정보를 이용해 주변 사업장을 검색
- 쓰기 요청보단 읽기 요청이 자주 발생
- QPS(Query Per Second)가 높다
    - 특정 시간대의 인구 밀집 지역일수록 그 경향 심함
- 무상태 서비스이므로 수평적 규모 확장 쉬움

## 사업장 서비스

- 사업장 소유주가 사업장 정보를 생성, 갱신, 삭제
- 기본적으로 쓰기 요청이며 QPS는 높지 않음
- 고객이 사업장 정보를 조회하며 특정 시간대에 QPS가 높아진다

## 데이터베이스 클러스터

- 주-부(primary-secondary) 데이터베이스 형태로 구성 가능
- 주 데이터베이스는 쓰기 요청을 처리하고 부 데이터베이스, 즉 사본 데이터베이스는 읽기 요청을 처리
- 데이터는 일단 주 데이터베이스에 기록된 다음에 사본 데이터베이스로 복사
    - 복제에 걸리는 시간 지연(delay) 때문에 주 데이터베이스와 사본 데이터베이스의 데이터에는 차이 있을 수 있음 (하지만 사업장 정보는 보통 실시간으로 갱신될 필요는 없어서 큰 문제가 되지 않음)

## 주변 사업장 검색 알고리즘

### **2차원 검색**

**주어진 반경으로 그린 원 안에 놓인 사업장을 검색하는 방법**

```sql
SELECT business_id, latitude, logitude,
FROM business
WHERE (latityde BETWEEN {:my_lat} - radius AND {:my_lat} + radius)
AND
	(longtitude BETWEEN {:my_long} - radius AND {:my_long} + radius)
```

이 질의는 테이블 전부를 읽어야 하므로 효율적이지 않다

→ 위도와 경도 칼럼 인덱스를 만들어 두면?

위도와 경도 칼럼에 인덱스를 만들어 놓으면 각각의 경도/위도에 대한 집합은 신속히 추출 가능하지만 주어진 반경 내 사업장을 얻으려면 이 두 집합의 교집합을 구해야 한다 → 이 연산은 각 집합에 속한 데이터의 양때문에 효율적 X

> 데이터베이스 인덱스로는 오직 한 차원의 검색 속도만 개선 가능하다!
>

- 지리적 정보에 인덱스를 만드는 방법
    - 해시 기반 방안: 균등 격자, 지오해시, 카르테시안 계층
    - 트리 기반 방안: 쿼드트리, 구글 S2, R 트리

💡

각 인덱스 구현 방법은 서로 다르지만, 모두 지도를 작은 영역으로 분할하고 고속 검색이 가능하도록 색인을 만드는 방식이다

</aside>

### **균등 격자**

**지도를 작은 격자 또는 구획으로 나누는 방법**

- 문제점

  데이터 분포(사업장 분포)가 균등하지 않고 주어진 격자의 인접 격자를 찾기 까다로울 수 있다. (다른 방안과 달리 격자 식별자 할당에 명확한 체계가 없음)


### **지오해시(Geohash)**

**2차원의 위도 경도 데이터를 1차원의 문자열로 변환**

- 비트를 하나씩 늘려가면서 재귀적으로 세계를 더 작은 격자로 분할해 나간다
    - 원하는 정밀도를 얻을 때까지 반복
- 통상적으로 base32 표현법을 사용
    - 구글 본사 지오해시 (길이=6) : 1001 10110 01001 10000 11011 11010 (base32 이진 표기) → 9q9hvu (base32)
- 12단계 정밀도 존재
    - 이 정밀도가 격자 크기를 결정 (격자가 클수록 정밀도 낮음 ⇒ 지오해시 길이 작음)
    - 최적 정밀도는 사용자가 지정한 반경으로 그린 원을 덮는 최소 크기 격자를 만드는 지오해시 길이

- 격자 가장자리 관련 이슈

  > 지오해시는 해시값의 공통 접두어(prefix)가 긴 격자들이 서로 더 가깝게 놓이도록 보장한다
  >
    1. 그 역은 참이 아니다

       아주 가까운 두 위치가 어떤 공통 접두어도 갖지 않을 수 있다

        ```sql
        SELECT * FROM geohash_index WHERE geohash LIKE '9q8zn%';
        ```

       따라서 위와 같은 단순 접두어 기반 SQL 질의문으로는 모든 주변 사업장을 가져올 수 없다

    2. 두 지점이 공통 접두어 길이는 길지만 서로 다른 격자에 놓이는 경우

       이를 해결하기 위해 보통 현재 격자를 비롯한 인접한 모든 격자의 모든 사업장 정보를 가져온다


- 표시할 사업장이 충분하지 않은 경우
    1. 주어진 반경 내 사업장만 반환한다
    2. 검색반경을 키운다
        - 지오해시 값의 마지막 비트를 삭제하여 얻은 새 지오해시 값을 사용해 주변 사업장을 검색하는 것
        - 그래도 충분한 사업장이 없을 경우 또 한 비트를 지워서 범위를 다시 확장하며 이를 반복하면 원하는 수 이상의 사업장을 얻을 때 까지 격자 크기가 확장된다

### **쿼드 트리**

격자의 내용이 **특정 기준을 만족할 때까지 2차원 공간을 재귀적으로 사분면 분할하는 데 사용되는 자료 구조**

> 쿼드트리를 사용한다는 것은 결국 질의에 답하는 데 사용될 트리 구조를 메모리 안에 만드는 것
>
- 쿼드 트리는 메모리 안에 놓이는 자료 구조일 뿐 데이터베이스가 아니다
- 이 자료 구조는 각각의 LBS 서버에 존재해야 하며, 서버가 시작하는 시점에 구축된다

```java
public void buildQuadtree(TreeNode node) {
	if(countNumberOfBusinessInCurrentGrid(node) > 100) {
		node.subdivide();
		for(TreeNode child : node.getChildren()){
			buildQuadtree(child);
		}
	}
}
```

- 쿼드트리로 주변 사업장을 검색하려면?
    1. 메모리에 쿼드트리 인덱스를 구축
    2. 검색 시작점이 포함된 말단 노드를 만날 때까지, 트리의 루트 노드부터 탐색한다. 해당 노드에 100개 사업장이 있는 경우에는 해당 노드만 반환하고 그렇지 않은 경우 충분한 사업장 수가 확보될 때까지 인접 노드도 추가

- 쿼드트리 운영 시 고려사항
    - 서버를 시작하는 순간 트리를 구축하면 서버 시작 시간이 길어질 수 있다
    - 사업장이 추가/삭제되었을 때 쿼드트리 갱신 문제
        - 수많은 키가 한번에 무효화되어 캐시 서버에 막대한 부하가 가해질 수 있음
        - 가장 쉬운 방법은 모든 서버를 한번에 갱신하는 것이 아닌 점진적으로 몇 개씩만 갱신하는 방식


### 구글 S2

쿼드트리와 같은 메모리 기반(in-memory) 방식으로 지구(sphere)를 힐베르트 곡선이라는 공간 채움 곡선을 사용하여 1차원 인덱싱하는 방안

- 힐베르트 곡선 상에서 인접한 두 지점은 인덱싱 이후 1차원 공간 내에서도 인접한 위치에 존재한다
- 지오펜스(geofence)를 통해 임의 지역에 다양한 수준의 영역 지정이 가능
    - 동적으로 영역을 지정할 수도 있고, 이미 존재하는 경계선들을 묶어 설정 가능
- S2가 제공하는 영역 지정 알고리즘을 통해 지오해시처럼 고정된 정밀도를 사용하는 대신, 최소 수준, 최고 수준, 최대 셀 개수 등을 지정 가능

## 데이터베이스의 규모 확장성

- 사업장 테이블
    - 사업장 ID를 기준으로 샤딩을 적용하면 좋다
        - 모든 샤드에 부하를 고르게 분산 가능, 운영 관리 쉬움
- 지리 정보 인덱스 테이블

  > 여기서는 지오해시를 사용
  >
    1. 각각의 지오해시에 연결되는 모든 사업장 ID를 JSON 배열로 만들어 같은 열에 저장하는 방안

       ⇒ 특정한 지오해시에 속한 모든 사업장 ID가 한 열에 보관된다 - `list_of_business_ids` (JSON 배열)

    2. 같은 지오해시에 속한 사업장 ID 각각을 별도 열로 저장하는 방안

       ⇒ 사업장마다 한 개 레코드 필요 - `business_id` 칼럼에는 1개 ID만 저장


    > 1의 경우 사업장 정보를 갱신/등록하려면 모든 JSON 배열을 다 읽은 후 수행해야 한다. 또한 병렬적으로 실행되는 갱신 연산 결과로 데이터가 소실되는 경우를 막기 위해 락을 사용해야 한다. 하지만 2의 경우 지오해시와 사업장 ID 칼럼을 합친 (geohash, business_id)를 복합 키로 사용하면 사업장 정보를 추가하고 삭제하기 쉽다. (락을 사용할 필요 없음)
    > 
    - 지리 정보 인덱스의 규모 확장
        
        관계형 데이터베이스 서버의 경우 부하 분산에는 두가지 전략 흔히 사용
        
        - 읽기 연산을 지원할 사본 데이터베이스 서버 늘림
        - 샤딩 적용
- 캐시

  > 가장 직관적인 캐시 키는 사용자 위치의 위도 경도 정보
  >
    - 사용자로부터 반환되는 위치 정보는 추정치일 뿐 정확하지 않음
    - 사용자가 이동하면 해당 위도, 경도 정보 미세하게 변경

      ⇒ 사용자 위치 정보는 캐시 키로 적합 X

    💡
    
    지오해시나 쿼드트리는 같은 격자 내 모든 사업장이 같은 해시 값을 갖도록 만들수 있기 때문에, 이 문제를 효과적으로 해결한다

        - 키: 지오해시 / 값: 해당 격자 내의 사업장 ID 목록
        - 키: 사업장 ID / 값: 사업장 정보 객체
    - 격자 내 사업장 ID
        
        사업장 정보는 비교적 안정적이라 특정 지오해시에 해당하는 사업장 ID 목록을 미리 계산한 다음 레디스 같은 키-값 저장소에 캐시할 수 있다

## 최종 설계도

### 주변 사업장 검색

1. 주변 반경 500미터 내 모든 식당을 찾는 경우, 우선 클라이언트 앱은 사용자의 위리와 검색 반경을 로드밸런서로 전송한다
2. 로드밸런서는 해당 요청을 LBS로 보낸다
3. 주어진 사용자 위치와 반경정보에 의거해 LBS는 검색 요건을 만족할 지오해시 길이를 계산한다
4. LBS는 인접한 지오해시를 계산한 다음 목록에 추가한다
5. 위 목록 내에 있는 지오해시 각각에 대해 LBS는 지오해시 레디스 서버를 호출하여 해당 지오해시에 대응하는 모든 사업장 ID를 추출한다
6. 반환된 사업장 ID를 가지고 사업장 정보를 레디스 서버를 조회하여 각 사업장의 상세 정보를 취득한다. 해당 상세정보에 의거해 사업장 ID와 사용자 간 거리를 계산후 우선순위를 매긴 다음 클라이언트 앱에 반환
